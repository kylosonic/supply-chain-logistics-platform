## 1. Purpose

This batch improves the parts of the product that make decisions from the customer's own
operational data. The goal is grounded decision support with visible evidence, not a generic chat
surface or an unverifiable "AI" label.

## 3. Implemented Behavior

### 3.1 Forecast evidence

- A chronological holdout uses the most recent 25% of available weeks (minimum one, maximum four).
- `quality` reports history weeks, holdout weeks, evaluated rows, MAE, WAPE, interpretation, and a
  caveat.
- Fewer than three weeks produces `insufficient_history`; no backtest is fabricated.
- Every point carries `planning_low` and `planning_high`. Bounds combine RandomForest tree spread
  with the held-out WAPE and are widened rather than narrowed by the error estimate.
- Model and quality caches are keyed by the full training-frame content, including the demand
  distribution, so equal totals with different weekly values cannot reuse stale evidence.
- The reported error is an aggregate held-out metric. It does not claim that every individual
  warehouse/SKU series has enough history or equally low error.

### 3.2 Route decision explanation

- The explanation is derived from the same persisted inputs and effective weights used for the
  selected route.
- Every greedy decision records the chosen stop, the actual runner-up, score margin, factor
  contributions, and capacity exclusions.
- The alternate-first-stop route is generated by rerunning the optimizer, not synthesized from
  static copy.
- Constraints distinguish max stops, mid-assignment capacity exclusions, and a final remaining
  capacity shortfall.
- The explanation states that it explains greedy choices and does not prove global optimality.
- With the current single-speed and single-cost inputs, the explanation states that weights change
  the objective value but not the nearest-stop ordering. This prevents the sliders from implying
  behavior the planner does not have.
- Explanations persist in `route_optimization_runs.explanation_json`; the column is nullable so
  older runs still load and report that no explanation was recorded.

### 3.3 Console

- Forecast cards show model, held-out error, history depth, evidence status, interpretation, and
  caveat. The chart renders point demand and planning bounds.
- Route results and history expose a "Why this route" brief with dominant factor, factor shares,
  constraints, runner-up scenario, and decision-by-decision evidence.
- A failed on-demand history fetch shows an error instead of an empty or invented explanation.

### 3.4 Grounded daily decision layer

- `GET /api/v1/ops/decision-brief`, `/cash-risk`, and `/exception-triage` are tenant-scoped and
  require active membership plus an effective viewer/operator/admin role.
- The brief is assembled by `app/services/decision_intelligence.py` from stored alerts, delayed
  shipments, low-stock inventory, unassigned route history, and open delivery cash. It reports
  `generated_by: grounded_rules`; no free-form query or autonomous state change exists.
- Cash-risk rows expose the driver, outstanding stop count, expected/collected/shortfall ETB,
  a bounded 0–100 score, and the factors that produced it. Deactivated/cancelled/failed records do
  not create cash obligations.
- Exception triage ranks open or acknowledged alerts by severity and age, returns the source alert
  ID as evidence, and suggests a human action. The suggestion is advisory; there is no endpoint
  that executes it.
- The console dashboard renders risks, ranked actions, cash radar, and triage with evidence and
  honest empty/failure states. It never renders an unsupported claim when the fact bundle is empty.
- The API contract lives in `app/schemas/decision.py`; the service and endpoints are covered by
  tests for populated, empty, cross-tenant, and org-less access.

### 3.5 Rerouting and weather truth

- No synthetic carrier, recovery time, or USD cost is generated.
- A rerouting candidate is only attached when an active saved schedule exists for the same origin
  and destination. Otherwise the alert carries `rerouting_status = no_saved_alternative`.
- Auto-resolve validates the proposed route and related shipment against the caller's organization
  before changing either record.
- Weather zones are explicitly labelled as simulated; the previous mock-storm fallback was removed.

## 6. Local Security Self-Review

This is an implementation self-review, not the independent `@security` gate.

- **Tenant boundary:** route explanations are returned only through the existing
  organization-scoped history lookup. A two-tenant regression test proves the other organisation
  receives 404 with no explanation payload.
- **Input boundary:** no new public request fields were added. The explanation is derived from the
  already-scoped warehouses, validated delivery payload, and effective optimizer weights.
- **Rendering:** all explanation fields are rendered as React text. There is no
  `dangerouslySetInnerHTML`/`innerHTML` use in the added components.
- **Storage:** the new JSON column contains warehouse codes, numeric scores, constraint copy, and
  limitations. It does not contain credentials, provider payloads, or user secrets.
- **Cache bounds:** both trained-model and forecast-quality caches are capped at 10 entries; quality
  cache entries are evicted in insertion order.
- **Migration:** additive nullable column; old code ignores it. Downgrade drops only the new column.
- **Residual risk:** independent security review must still assess the final diff and deployment
  context.

## 7. Deliberate Non-Goals

- No chatbot or natural-language interface is added.
- No claim of causal demand accuracy or global route optimality is made.
- No production migration is applied and no deployment is performed in this batch.
- Simulated weather, ETA confidence limitations, and saved-route-only rerouting constraints are not
  hidden behind new copy.

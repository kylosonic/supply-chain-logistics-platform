## 2. Goal

Restructure `apps/ops-console` routing so the workspace shell (`Layout`: sidebar, top shell, `CapPitchBanner`, mobile drawer) mounts exactly once per authenticated session with pages swapping inside a nested `<Outlet/>`, and lift the live WebSocket out of `DashboardPage` into that persistent shell so it opens once per session with debounced, payload-scoped background invalidation and silent failure — with zero new runtime dependencies.

## 3. Ground-truth decisions

1. **Route composition: layout route owns ONE auth-level `ProtectedRoute`; every child route keeps its own role-gated `ProtectedRoute` around the page element.** Concretely: `<Route path="/" element={<ProtectedRoute><Layout/></ProtectedRoute>}>` (auth-only — NO `allowedRoles` prop, preserving today's unauthenticated redirect `Navigate to="/login" state={{from: pathname}} replace` BEFORE the shell can mount, byte-for-byte) with children where the dashboard is the **index route** (`<Route index element={<ProtectedRoute><DashboardPage/></ProtectedRoute>}/>`) and every other console path is a child route whose element is `<ProtectedRoute allowedRoles={[exact same array as today]}><Page/></ProtectedRoute>`. Role mismatch redirects to `/unauthorized` `replace` exactly as today — the child gate still performs it; the shell may render for one commit before the redirect, but `Navigate` commits within the same render pass (no painted frame). `/login`, `/unauthorized`, and the top-level `<Route path="*" element={<Navigate to="/" replace/>}>` stay exactly where they are today (outside the layout route). This is the ticket's option (b) — per-route `ProtectedRoute` preserved, only `Layout` hoisted — plus an auth-only gate on the layout route so unauthenticated users never render the shell (current behavior).
2. **Suspense moves inside the shell.** The current top-level `<Suspense fallback={<RouteFallback/>}>` would unmount the whole tree (including the hoisted `Layout`) while a lazy page chunk loads — a first-visit shell remount. The nested boundary is therefore required: `Layout` renders `<Suspense fallback={<RouteFallback/>}><Outlet/></Suspense>` so the shell stays mounted during chunk loads; only the content area shows the existing "Loading workspace surface..." fallback. The `RouteFallback` markup moves into `Layout.tsx` (identical copy, exported so `App.tsx` reuses it for the `/login` + `/unauthorized` lazy chunks at the top level). After the first visit to a page its chunk is cached, so no subsequent suspension occurs.
3. **Live socket owner = `SessionLiveUpdates` component mounted once inside `Layout`.** It calls the existing, UNCHANGED `useLiveUpdates({ getToken, enabled: Boolean(user), onMessage: publishLivePayload })` — `getToken` is a stable `useCallback([])` (AuthContext) so the effect cannot re-run on layout re-renders; `Boolean(user)` gates the socket exactly like today's dashboard gating; effect cleanup closes the socket on logout (session end) and the next login opens a fresh one — precisely "once per workspace session" (NB-56.1). `publishLivePayload` is a module-stable reference → no `onMessage` churn.
4. **Live payload distribution = module-level external store in `useLiveUpdates.ts`** (same pub/sub pattern Phase 1 established in `api.ts`; no context, no new dependency). Exports: `publishLivePayload(payload)` (sets the latest payload + notifies listeners), `getLivePayload()` (stable snapshot getter), `useLivePayload()` (via `useSyncExternalStore` — with `getServerSnapshot` supplied so SSR is safe; used by the dashboard chip), `useLivePayloadStream(listener)` (fires the listener ONLY on new publishes, never on mount — used by RoutesPage and DashboardPage invalidation so a stale last payload is never re-applied on page mount), and `resetLivePayloadStore()` (test seam). Rationale: `renderToString` cannot run effects, so the socket itself is untestable here; the store is the testable seam.
5. **Invalidation set — payload-scoped, evidence from `hooks/queries.ts` consumers:** the payload carries exactly `inventory_overview`, `route_summaries`, `forecast_preview`. Mapping: `inventory_overview` → invalidate `['inventory']` (only consumer: `useInventoryOverview`, DashboardPage only), `route_summaries` → invalidate `['routes']` (matches `['routes','schedules']` — DashboardPage only via react-query; `['routes','history']` has ZERO consumers; RoutesPage reads schedules/history via direct service calls into local state, verified: it imports only `useActivationState` from `hooks/queries`), `forecast_preview` → invalidate `['forecast']` (only consumer: `useForecast(4)`, DashboardPage only). **Dropped from live invalidation:** `['shipments']`, `['subscriptions']` (payload never contains that data; other pages read these via service-direct local state, not react-query — AccountPage fetches usage/subscription via services), and `['activation']` (payload never contains activation data; invalidating it today only refetches `CapPitchBanner`/`ActivationBanner`/RoutesPage/UploadPage unnecessarily; they refresh via their 30s staleTime). Manual "Refresh data" keeps the existing 6-group `useInvalidateDashboard()` — user-initiated full refresh is unchanged.
6. **Invalidation timing — trailing-edge debounce, 15s max-wait, dashboard-mounted-only.** New pure factory `createCoalescedInvalidator(windowMs = LIVE_INVALIDATION_WINDOW_MS = 15_000, invalidateFn)`: the first call within a window starts a timer; subsequent calls only replace the held latest payload; at exactly `windowMs` after the first call the invalidator flushes with the LATEST payload; `dispose()` cancels the pending timer. Guarantee: **at most one invalidation per 15s window, last payload wins, no starvation** (strict reading of TECH-73 "~10-15s"). The invalidator is invoked only from a `useLivePayloadStream` effect in DashboardPage → invalidations are impossible while the dashboard is unmounted (stream listeners fire only while subscribed; react-query's `refetchOnMount` for stale queries covers freshness on dashboard re-entry — no mount-time invalidation needed). No invalidation is ever triggered by navigation itself, so `CapPitchBanner` never refetches on page switches (NB-55.3).
7. **Socket reconnect policy: connect-once-and-stop — no reconnect, no backoff.** Evidence/justification: the existing `useLiveUpdates` has no `onerror`/`onclose` handlers — a failed socket today fails silently and never retries; the per-page-visit churn the ticket describes comes from the socket living in unmounting pages, which this phase eliminates. Adding exponential backoff would introduce a new timer lifecycle in the shell (unmount cleanup, tests, serverless WS-handshake hammering on Vercel) with zero operator-visible benefit: freshness is already covered by react-query staleTime refetches and the manual "Refresh data" button. NB-56.3 is satisfied: unavailable socket → no UI error path exists, no retry churn, app keeps working. The `_wsToken` module cache stays (no token refetch churn).
8. **"Live sync" chip stays on DashboardPage and reads the shared store.** `useLivePayload()?.server_time` replaces the local `lastLiveUpdate` state: the timestamp survives dashboard unmount/remount because the store is session-scoped, so the chip never flickers/disappears per navigation. Copy preserved verbatim: `Live sync {new Date(server_time).toLocaleTimeString()}`, emerald pill + dot markup unchanged.
9. **RoutesPage consumes the shared stream instead of its own socket.** Its `useLiveUpdates` call (the second, today-unnoticed socket) is replaced by `useLivePayloadStream` + an effect doing exactly what its old `onMessage` did: `setSchedules(payload.route_summaries)`. Mount freshness stays with the existing `loadSchedules()` service call (which also wins over any stale snapshot because the stream never fires on mount).
10. **Test environment constraint (unchanged from Phase 1):** vitest runs in the node environment (no jsdom installed; smoke tests use `renderToString`; effects never flush). "Layout stays mounted across navigation" cannot be asserted server-side; it is pinned by a static composition guard + the new Layout SSR smoke test, with final proof in the human UAT (PM plan §5.2).

## 6. Acceptance checkpoints (verbatim NB rules from `pending-behaviors.md`)

**NB-55** (TECH-72): (1) When the operator moves between pages, the sidebar (brand block, both navigation groups, identity footer) stays mounted and does not rebuild or flicker. (2) The top shell (context label, page descriptor, role and user chips) stays mounted across page switches. (3) Persistent banners (usage cap, upgrade pitch, activation state) stay mounted and do not refetch or flash on navigation. (4) The active page marker in the sidebar is always correct after a page switch. (5) On mobile, the navigation drawer state the operator left is preserved where sensible.

**NB-56** (TECH-73): (1) The live data connection opens once per workspace session and remains open while the operator works; leaving the dashboard and returning to it does not reopen or replay the connection. (2) When live data arrives, dashboard surfaces update quietly in the background — the operator never sees the dashboard blank out, replay loading placeholders, or rebuild panels because of a background refresh. (3) If the live connection is unavailable, the operator still sees the last known data and the application keeps working; no errors are shown and the console does not retry aggressively on every page visit.

2. **`hooks/useLiveUpdates.test.ts`** (node env): (a) `publishLivePayload` updates `getLivePayload`; (b) `useLivePayloadStream` listener fires only on NEW publishes — never at subscribe time; (c) multiple listeners + unsubscribe semantics; (d) `resetLivePayloadStore` clears payload + listeners; (e) SSR safety probe: `renderToString` a component using `useLivePayload` — renders nothing when the store is empty, renders the seeded `server_time` when pre-published (proves the chip's SSR path and that `useSyncExternalStore` with `getServerSnapshot` is render-safe).
